# 完整 key 去重修复验收

> **历史兼容算法**：本文说明旧 `/api/jobs` 执行链的完整 key 归约规则，旧接口仍保留。当前新上传使用固定标签与跨视图匹配，不是这里的算法。参见 [当前第三阶段](cross-view-entities.md) 和 [文档目录](README.md)。

## 问题与规则

旧流程允许第三阶段 AI 改写标签和长度，再以数量分配守恒作为通过条件，导致不同标高平面上的同规格、同长度构件被误合并。

第二阶段接收响应后补入图纸标题对应的所属面，规范化标签，计算名义长度，记录 `source_plane_tag` 和 `member_key`。原观察 ID、行数、`member_cnt`、位置、长度输入及证据均保留。key 为规范化的 `(spec, view_tags, length_mm)`；组合前缀参与身份，标签顺序不影响身份。

第三阶段由程序按完整 key 分组。同一来源内同 key 的数量相加；跨来源同 key 且数量一致时只保留一组。key 不同绝不合并，不允许通过标签并集、改规格或改长度制造相同 key。数量不一致时各来源独立保留并记录冲突，不取最大/最小值。缺失长度等项目保留在待处理台账，不静默丢弃。组合件最终只展开一次。

第三阶段不再调用 AI 提案。历史 AI 提案仍可查看，但任何提交都必须满足来源 key 与结果 key 完全一致。
